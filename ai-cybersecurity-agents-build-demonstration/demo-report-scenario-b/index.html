Demo Report: Scenario B, Attacking Address Blocked

November 24, 2026. Reviewed and signed off by Jessica A. Miller, November 24, 2026.

What this report is

A record of a controlled demonstration. One address flooded a test site with requests, the agent detected the pattern at the edge, blocked that address for one hour, and the site stayed up for everyone else through the whole event. This report shows the record.

The test site

Ashford & Locke, a fictional law office test site built for this demonstration. For this test the site ran live on Cloudflare Pages at ashford-locke.pages.dev (project ashford-locke, deployment 13bfe4ca), and it was verified returning 200 before the flood started.

The AI Cybersecurity Agent™ sat in front of the site as an edge worker at https://cybersecurity-agent.millrjess.workers.dev/, passing requests through to the Pages site. The AGENT_STATE KV binding was intact through the deploy. No live site, no client site, and no production site was touched.

The attack

A flood of 120 requests from one address, on one persistent connection, sent as fast as the connection allowed, over 17.6 seconds.

The playbook rule that covers this attack pre-authorizes blocking one attacking address for a set time when it sends more than 100 requests in 60 seconds. The block length is one hour. The count lives in a Durable Object, which counts every request as it arrives, so the 60-second window holds at flood speed. The threshold of 100 requests is unchanged.

An earlier test ran under a five-minute window, because the count then lived in KV and a KV write takes about a second to become visible. The count has since moved to a Durable Object, and this run used the 60-second window.

What happened

  • 08:27:45 AM: Flood starts. Requests 1 to 100 pass through to the site.
  • 08:28:01 AM: Request 101 arrives. The count passes 100. The agent writes the block and returns 403.
  • 08:28 AM: Requests 101 to 120 all return 403. The address is blocked.
  • 08:28 AM, during the block: The site loads normally from another address. I verified this from a different address, which returned 200 through the worker URL while the flood address was blocked. The site stayed up for everyone else.
  • 09:28:01 AM: The block lifts, one hour after it was set, per the setting. I did not watch the live expiry happen in real time. The expiry path is proven by the local test suite, where a blocked address passes again after the block time, and the block record below carries the exact end time.

120 requests sent, 100 returned 200, 20 returned 403, first 403 at request 101, zero 500 errors during the flood.

The evidence

  • Block record, from the agent's KV store: address 2606:54c1:1:230::501:3f, requests counted 101, block set November 24, 2026, 08:28:01 AM EST, block lifts November 24, 2026, 09:28:01 AM EST, block length one hour.
  • Per-request record: requests 1 to 100 returned 200 and the site served normally. Requests 101 to 120 returned 403. The first block came at request 101, exactly the threshold.
  • Evidence files: flood.py (the flood script), flood-results.json (per-request status codes), flood-run.log (the run output), flood-summary.md (the run summary).

What the agent did, and what I did

The agent counted the requests, detected the flood at the edge, and blocked the address under the playbook rule that pre-authorizes this action. The agent logged the block with the address, the count, and the set and lift times.

I did not approve this block in advance of the request, because the playbook already authorizes it. That is the rule the agent runs under: Monitor. Detect. Respond. I review. I reviewed the record after the run. The block was set at the standard 100-request threshold, not the 50-request repeat-offender threshold, so this address had not been blocked before.

What the run found

First, the Durable Object count held at flood speed. The flood sent 120 requests as fast as the connection allowed, and the block still landed exactly at request 101, with zero 500 errors. The earlier KV counting could not do this: a KV write takes about a second to become visible, so the count grew about one per second and needed a five-minute window. The move to Durable Objects fixed that. The earlier fix, wrapping every KV read, write, and delete so a failure is logged and the request passes through, still stands behind it.

Second, this run does not prove an under-a-second block. The connection could only send about 7 requests per second, so the block landed about 16 seconds after the flood started. The count is real time, but the test connection was the limit, not the agent. No under-a-second claim is made here.

Third, the KV block record was written to the store and read back after the run, even though the free-tier KV write quota was expected to be exhausted until 7 PM EST. The record is in the store, with the address, the count, and the set and lift times.

What this proves, and what it does not

This proves the agent detects a request flood at the edge, blocks the attacking address at exactly the threshold, keeps the site up for everyone else, and logs the whole event with the address and the times. The proof is the record above, not a claim.

This does not prove the agent stops every attack. The demonstration used one flood pattern on a test site. The live block expiry was not watched in real time, and the expiry path is proven by the local tests only. The flood came from this machine's egress address, which rotates between runs, and the block is per address. The first demonstration, a known-malware file restored from backup, ran the same morning.
